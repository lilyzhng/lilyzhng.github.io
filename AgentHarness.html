ANATOMY

Six Layers of an Agent Harness

From your keyboard to the model's response, your message passes through six layers. Click any layer to see what it does.

📜
System Prompt — The DNA
Thousands of tokens that define personality, rules, and capabilities

Before the model sees your message, it reads a long system prompt that tells it who it is, how to behave, and what rules to follow. Claude Code's system prompt is 3000+ tokens, heavily structured with markdown headers and explicit do/don't rules. A generic harness might use 10 words: "You are a helpful coding assistant."

This is the single highest-leverage text in the entire system. A vague prompt produces vague behavior. A precise prompt produces precise behavior.

The system prompt is like a job description — a detailed one produces a focused employee, a vague one produces someone who guesses
📚
Context Injection — What the Model Knows About You
CLAUDE.md, auto-memory, git status, credentials, session state

Claude Code loads your CLAUDE.md files (project rules like "never push to main"), auto-memory (cross-session learning), git status (current branch, recent commits), and project structure. All of this is injected into the system prompt before the model sees your message.

This is why your instruction "never push to main" works in Claude Code but not in Cursor — it's injected directly where the model reads it on every turn.

Like a briefing packet given to a consultant before they start work — the more context, the less time wasted asking basic questions
🔧
Tool Registry — What the Model Can Do
Read, Edit, Glob, Grep, Bash, WebSearch, sub-agents

Tools are functions the model can call. The quality of tool descriptions matters enormously — they tell the model when to use each tool, not just what it does. Claude Code has ~12 specialized tools, each with a careful description. A generic harness might give the model just run_command and hope for the best.

Key design choice: Claude Code's Edit tool does surgical string replacement (specify only what changed). Some harnesses use whole-file rewrites, which waste tokens and introduce errors.

A surgeon with a scalpel vs. a surgeon with a chainsaw — both can "edit" tissue, but precision tools produce better outcomes
🔄
Agentic Loop — The Engine
Multi-turn cycle: model thinks → calls tools → sees results → repeats

This is the heart of the harness. When you send a message: (1) the model decides what tool to call, (2) the harness executes it, (3) the result is fed back, (4) the model decides the next action. This loop continues until the model has enough information to give you a final answer.

A good harness lets the model loop 10-20 times autonomously — reading files, running tests, fixing errors, re-running. A limited harness might cut off after 2-3 turns.

Like a chef tasting as they cook — taste, adjust, taste again. Cutting them off after one taste means undercooked food
🗃
Context Management — Long-Term Memory
Compression, summarization, priority ordering

Every model has a finite context window. After dozens of file reads and tool calls, the conversation history fills up. A naive harness crashes or silently drops old messages. A good harness compresses old turns — asking a fast model to summarize them — while keeping recent context intact.

Claude Code also orders context by priority: system prompt and user instructions first, then recent tool results, then older history. This ensures the model always sees the most important information.

Like meeting notes — you don't re-read every email from 3 months ago, you keep a summary and focus on this week's updates
🔒
Permissions & Error Recovery
Safe tools auto-run, dangerous tools need approval, errors feed back to the model

Claude Code categorizes tools by risk: read-only tools (Read, Grep, Glob) run automatically, while modification tools (Edit, Bash, Write) prompt the user. When a user denies a tool call, the denial is fed back to the model as a result, so it can adjust its approach instead of getting stuck.

Similarly, when a tool throws an error (file not found, test failed), the error message is fed back. The model reads it and self-corrects on the next turn. A naive harness would just crash.

Like a new hire who checks with their manager before making big decisions, and learns from mistakes instead of freezing

The Five Key Differences

Each of these layers independently improves the model's behavior. Together, they compound.

1

System Prompt: Generic vs. Model-Specific

The highest-leverage text in the entire system

Generic (Cursor-like)

  • "You are a helpful coding assistant"
  • Must work for GPT-4, Claude, Gemini
  • No model-specific phrasing
  • ~10-50 tokens
  • No behavioral rules or examples

Model-Specific (Claude Code)

  • 3000+ tokens of structured instructions
  • Co-evolved with Opus — tested for which phrasings it responds to best
  • Explicit do/don't rules with examples
  • Tool-specific guidance ("use Read, not cat")
  • Behavior calibration ("don't over-engineer")

system = "You are a helpful coding assistant."

# Claude Code (simplified excerpt):
system = """You are Claude Code, Anthropic's official CLI.

# Tools
- Use Read instead of cat/head/tail
- Use Edit for surgical string replacement
- Use Grep instead of grep or rg

# Behavior
- Read files before editing them
- Don't over-engineer or add features beyond what was asked
- If a tool call fails, try a different approach
- If the user denies a tool, don't re-attempt it
..."""
2

Surgical Edit vs. Whole-File Rewrite

The tool design that saves thousands of tokens per edit

Some harnesses give the model an edit_file(path, new_content) tool — the model must output the entire file even if only one line changed. Claude Code's Edit tool takes old_string and new_string — the model only specifies the diff.

Whole-File Rewrite
Model outputs: 890 lines (entire file)
Lines actually changed: 1
Risk: could accidentally delete other code
No uniqueness check
Tokens wasted: ~2000
Surgical Replacement
Model outputs: 2 strings (old → new)
Lines actually changed: 1
Uniqueness check: old_string must appear exactly once
Precise diff visible to user
Tokens used: ~50
# Whole-file rewrite (what some harnesses do):
def edit_file(path: str, new_content: str):
    with open(path, "w") as f:
        f.write(new_content)  # entire file rewritten

# Surgical replacement (what Claude Code does):
def edit_file(path: str, old_string: str, new_string: str):
    content = open(path).read()
    assert content.count(old_string) == 1  # uniqueness check!
    content = content.replace(old_string, new_string, 1)
    with open(path, "w") as f:
        f.write(content)

The safety net that also makes the model smarter

The punchline: SofaGenius wraps Claude with tools (W&B monitor, SQL analyst, HF scout), system prompts (per-agent instructions), context injection (pre-resolved W&B identity, session state, run aliases), and an agentic loop (base.py) — the exact same pattern that makes Claude Code outperform Cursor.

How SofaGenius Maps to the Six Layers

1. System Prompt Each subagent has its own prompt (training.SYSTEM_PROMPT) with tool selection rules, behavior guidelines, and domain-specific instructions.
2. Context Injection _build_wandb_context() pre-resolves your W&B entity + projects. _build_launch_context() injects the last-launched run ID. _build_alias_context() maps friendly names to run IDs.
3. Tool Registry 5 subagents × 3-8 tools each. Rich descriptions tell the model WHEN to use each tool. CARD_TOOL_MAPPING maps tools to visual card types.
4. Agentic Loop base.run_subagent() loops up to 10 turns. Emits SSE events (text, tool_call, tool_result, card, done) for real-time streaming.
5. Context Management Session state (_session_contexts) persists across messages. _extract_event_context() captures launch/health card data for future reference.
6. Error Recovery _execute_tool() wraps every tool call in try/except. Errors are JSON-encoded and fed back to Claude as tool results.

Plus two layers Claude Code doesn't need:

Intent Routing _classify_intent() uses Haiku to route to 6 specialized subagents. Claude Code doesn't need this — it's one agent for all coding tasks.
Credential Isolation _inject_credentials() temporarily injects user's W&B/HF tokens into env vars during tool execution, then restores. Multi-user safety.
MCP & TRAINING

Two Paths to a Better Agent

Improving the software around the model vs. improving the model itself — they're complementary, not alternatives.

The key confusion: When people say "training an agent," they might mean two very different things. Harness engineering improves the code that wraps the model (system prompts, tool descriptions, loop logic) — no gradients involved. MCP trace fine-tuning trains the model's actual weights to be better at tool calling — real training with GPUs and loss functions. Both make agents better, but through completely different mechanisms.

PATH A

Harness Engineering

Improve the software around the model (no gradients)
  • What changes: Code — system prompts, tool descriptions, loop logic, context injection
  • Method: Manual iteration + optional automated prompt optimization (DSPy)
  • Uses GPUs: No
  • Benefits all models: Yes — swap in any model and it benefits from the improved harness
  • Maturity: Production-ready. This is how Claude Code, SofaGenius, and most agent systems are improved today
This is everything we covered in the sections above — system prompt engineering, surgical Edit tool design, CLAUDE.md injection, permissions, context compression.
PATH B

MCP Trace Fine-Tuning

Train the model's weights to be better at tool calling
  • What changes: Model weights — the neural network parameters themselves
  • Method: SFT or GRPO with gradient descent on tool-calling traces
  • Uses GPUs: Yes
  • Benefits all harnesses: Yes — the model itself becomes better at tools, regardless of which harness runs it
  • Maturity: Early research / emerging. Backend.AI's MCP Sidecar is one of the first concrete examples
This is real training — collecting agent traces, creating datasets, running SFT or GRPO on GPUs to improve the model's tool-calling ability.
1

Where MCP Fits In the Picture

MCP is a protocol inside the harness's tool layer — it enables both paths

MCP (Model Context Protocol) is a standard format for tools to advertise their capabilities to LLMs. It lives inside the harness's tool layer — it's not the whole harness, and it's not model training. But it enables both paths:

# MCP's place in the architecture:

HARNESS
  ├── System Prompt
  ├── Agentic Loop
  ├── Context Injection
  ├── Permissions
  └── Tool Layer
      ├── Native tools (defined in your code)
      │   e.g., SofaGenius's analyze_run_health
      │
      └── MCP servers (standard protocol) ◄── THIS
           e.g., GitHub MCP server, Slack MCP server
           Tools advertised via JSON-RPC schemas

MCP standardizes how tools describe themselves. This is useful for harness engineering (one format to support instead of per-tool custom code), model training (consistent format means more uniform training data), and interoperability (tools built for Claude Code work in any MCP-compatible harness).

2

How MCP Trace Fine-Tuning Works

Collect real agent sessions, use them to train the model's tool-calling ability

A trace is a recording of a complete agent session: what the user asked, which tools the model called, what results came back, and whether the final outcome was good. Here's what a trace looks like:

User
"What's the weather in Tokyo and book me a flight there"
Model → Tool Call
weather_tool("Tokyo") ← correct tool selection
Tool Result
{"temp": 15, "condition": "cloudy"}
Model → Tool Call
flight_search("SFO", "TYO") ← correct next step
Tool Result
[{price: 850, airline: "JAL"}, ...]
Model → Final Response
"It's 15°C and cloudy in Tokyo. I found flights from $850 on JAL." ← knows when to stop

The training process uses these traces as (input, output) pairs:

🔧

✅

Case Study: Backend.AI's MCP Sidecar Model

SFT failed, GRPO worked — a real example of MCP trace fine-tuning

Backend.AI built a small "sidecar" model that helps open-source LLMs (Llama, Gemma) comply with MCP format. The problem: these models were never trained on MCP tool schemas, so they format tool calls incorrectly. The sidecar sits beside the main LLM and "fixes" its output into proper MCP format.

Attempt 1: SFT — Failed
Used GPT-5 to correct imperfect JSON, then trained the sidecar via SFT to mimic the corrections.

Problem: Since modern LLMs already produce 90%+ valid JSON, the model learned to copy the input, not correct it. The token overlap was too high for SFT to find the signal.
Attempt 2: GRPO — Worked
Switched to reinforcement learning using GRPO (same algorithm SofaGenius uses for training). Used MCP-Bench metrics as reward signals.

Result: Significant improvements in JSON formatting, tool selection, schema adherence, and parameter validity. The model learned to fix, not just copy.

They evaluated on MCP-Bench — a benchmark with 28 MCP servers (Google Maps, Wikipedia, Steam). Open-source models scored poorly because they were never trained on MCP tool-calling formats. The sidecar patches this gap at minimal cost, without modifying the main LLM.

4

97% of MCP Tool Descriptions Have "Smells"

Fixing tool descriptions is a low-hanging fruit that improves both paths

Recent research analyzed 856 MCP tools and found that 97.1% have at least one quality defect ("smell") in their descriptions. Just like code smells, these aren't technically broken but degrade the model's ability to use the tool correctly.

56%
Unclear Purpose
Tool doesn't explain what it does
97%
At Least One Smell
Missing guidelines, limits, or examples
+6%
Success Improvement
After augmenting descriptions

The six quality components: Purpose (what does it do?), Guidelines (when should you use it?), Limitations (what can't it do?), Parameter Explanation (what do the inputs mean?), Length/Completeness (enough detail?), and Examples (show me a call). Enriching descriptions with these components improved task success by ~6% — a free improvement that requires no model training.

Uses GPUs No Yes

The bottom line: These two paths are complementary. A better harness helps any model perform better (Path A). A fine-tuned model is better at tool calling regardless of which harness runs it (Path B). The best agent systems will use both — a well-engineered harness running a model that's been fine-tuned for tool use.

What Stays the Same?

The harness architecture is unchanged — only the model inside changes
Unchanged (Harness)
  • • Context injection (W&B identity, session, aliases)
  • • Intent routing architecture
  • • Tool definitions and dispatch
  • • Card emission via CARD_TOOL_MAPPING
  • • SSE streaming to frontend
  • • Permission model and error recovery
Changed (Model)
  • • Which tool to call and when
  • • Argument formatting accuracy
  • • Number of loop iterations needed
  • • When to stop and give a final answer
  • • JSON formatting compliance
  • • Domain-specific reasoning

This is why the harness vs. model distinction matters. The harness is the frame. The model is the engine. You can upgrade the engine without redesigning the frame — and you can improve the frame to make any engine perform better. The best systems do both.

GLOSSARY

Key Terms

The vocabulary of agent harnesses, explained in plain English.

Core Concepts
Agent Harness
The complete software layer between you and the LLM. Includes system prompt, tool definitions, agentic loop, context management, and permission system. The same model inside different harnesses produces different behavior — this is why Opus feels better in Claude Code than in Cursor.
The operating system that a CPU runs inside — same chip, different OS, different experience
System Prompt
A block of text sent to the model before your message, on every turn. Defines personality, rules, capabilities, and behavioral constraints. Claude Code's is 3000+ tokens. A generic harness might use 10 words.
A job description that the employee re-reads every morning before starting work
Tool Definition
A JSON schema describing a function the model can call. Includes name, description (tells model WHEN to use it), and input parameters. The quality of descriptions directly affects model behavior — a vague description produces random tool usage.
A labeled toolbox — clear labels ("Phillips head screwdriver, use for small screws") vs. unlabeled drawers
Agentic Loop
The multi-turn cycle where the model calls a tool, sees the result, decides the next action, calls another tool, and repeats until it has enough information to give a final answer. The number of allowed turns determines how much autonomous work the model can do.
A chef tasting soup repeatedly — taste, adjust salt, taste again, add pepper, taste again, serve
Context & Memory
CLAUDE.md
A markdown file in your project root that contains persistent instructions for Claude Code. Rules written here are injected into the system prompt on every turn. Examples: "never push to main", "use pytest for tests", "follow our design system." Also supports a global version at ~/.claude/CLAUDE.md.
A team wiki that every new hire reads on day one — and re-reads every morning
Context Window
The maximum amount of text a model can "see" at once (input + output). When the conversation history exceeds this limit, something must be dropped or compressed. Claude's context window is ~200K tokens.
The size of your desk — you can only spread out so many papers before you have to file some away
Context Compression
When the conversation history nears the context window limit, old turns are summarized by a fast model (Haiku) and replaced with a compact summary. Recent turns are kept verbatim. This prevents crashes and information loss.
Meeting minutes — you don't re-read every word from last month's meetings, you keep a summary
Tool Design
Surgical Edit
An edit tool that takes (old_string, new_string) and replaces only the exact match. Enforces uniqueness (old_string must appear exactly once). This is how Claude Code's Edit tool works — dramatically fewer tokens and errors than whole-file rewrites.
Find-and-replace in a text editor, but with a safety check that prevents ambiguous replacements
SSE (Server-Sent Events)
A protocol for streaming data from server to browser. Agent harnesses use SSE to stream the model's response in real-time: text chunks, tool call notifications, card data, and completion signals. This creates the "typing" effect you see in Claude Code and SofaGenius.
A live sports ticker — updates appear as they happen, you don't have to refresh
Safety & Control
Permission Model
A system that categorizes tools by risk level. Read-only tools (Read, Grep) run automatically. Modification tools (Edit, Bash) require user approval. When the user denies a call, the denial is fed back to the model so it can adjust its approach.
A new employee who checks with their manager before making purchases over $100
Error Recovery
When a tool call fails (file not found, test failed, permission denied), the error is fed back to the model as a tool result. The model reads the error and self-corrects on the next turn. A naive harness would crash or get stuck.
A GPS that reroutes when you miss a turn, instead of saying "route calculation failed"
Intent Routing
Using a fast, cheap model (Haiku) to classify the user's intent and route to a specialized subagent. SofaGenius uses this: "check my training" → Training Agent, "find a dataset" → Scout Agent. This keeps each agent focused with a small, relevant tool set.
A hospital triage desk — quick assessment of your symptoms, then you're sent to the right specialist
MCP & Model Training
MCP (Model Context Protocol)
A standard protocol for tools to advertise their capabilities to LLMs via JSON-RPC schemas. MCP lives inside the harness's tool layer. It standardizes how tools describe themselves, enabling interop — a tool built for Claude Code works in any MCP-compatible harness.
USB-C for AI tools — one standard plug so any device works with any port
MCP Trace Fine-Tuning
Training a model's weights on recorded agent sessions (user request → tool calls → results → final answer). The model learns which tool to pick, how to format arguments, and when to stop. This is Path B — improving the model itself, not the harness code.
A new doctor studying case files from experienced doctors — learning diagnosis patterns from real patient interactions
SFT (Supervised Fine-Tuning)
Training a model to imitate correct examples by minimizing the difference between its output and the reference output. Simple but can fail for tool calling — the model may learn to copy surface patterns (90% token overlap) rather than learning the underlying correction logic.
Copying an expert's homework — you reproduce the answers but don't learn the reasoning
GRPO (Group Relative Policy Optimization)
A reinforcement learning method that scores multiple model outputs and pushes the model toward better ones. Unlike SFT, the model explores different strategies and is rewarded for correctness, not imitation. Backend.AI found GRPO succeeded where SFT failed for MCP compliance.
Learning to cook by trying variations and keeping the recipes that taste best, rather than memorizing one cookbook
Sidecar Model
A small, specialized model deployed alongside the primary LLM. It intercepts and corrects the primary model's tool calls to comply with MCP format. Useful when you can't fine-tune the primary model (e.g., it's a closed API like Claude or GPT).
A translator sitting next to a foreign diplomat — the diplomat speaks, the translator fixes the grammar for the audience
MCP-Bench
A benchmark suite with 28 real MCP servers (Google Maps, Wikipedia, Steam, etc.) for evaluating how well a model handles tool calling. Open-source models score poorly because they were never trained on MCP formats — this is the gap sidecar models aim to fill.
A driving test with 28 different road scenarios — measures whether you can actually drive, not just recite the manual
Tool Description Smells
Quality defects in MCP tool descriptions: missing parameter explanations, vague descriptions, no usage examples, inconsistent formatting. Research shows 97% of MCP tools have at least one smell. Augmenting descriptions with examples and constraints improves task success by ~6%.
Poorly labeled medicine bottles — "take as needed" vs. "take 2 tablets with food every 8 hours for pain"
